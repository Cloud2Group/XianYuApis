# XianYuApis 产品领域模型

- 层级：L1
- 状态：Draft
- 更新时间：2026-07-28

## 文档职责

本文件定义产品中的核心角色、业务对象和它们之间的关系。具体 API、存储结构和实现方式不在本文件中决定。

## 已确认角色

### 平台负责人

定义项目目标、运营方向和关键业务取舍。

### 账号主

拥有一个或多个闲鱼账号，并将卖家运营权限授权给平台的个人或合作主体。

### 内部运营人员

代表平台处理运营任务、异常和后续人工流程。

### 闲鱼买家

在闲鱼内与被托管账号咨询、下单和交易的外部用户。

### API 调用者

向标准闲鱼 API 发出操作命令的程序。第一阶段主要是内部脚本和测试工具，未来可以是第三方软件或 AI Agent。

### Actor

发起 Query、Command 或管理操作的人或程序。Actor 类型包括平台负责人、内部运营人员、内部脚本、系统任务，以及未来的 AI Agent 和第三方应用。

每个 Command 必须关联明确 Actor，不存在匿名业务操作。

## 已确认核心对象

### 闲鱼账号

被平台运营的闲鱼卖家身份，是所有闲鱼 API 操作的目标对象。

### Account Runtime

一个闲鱼账号对应的逻辑运行环境，持有该账号的会话状态、设备身份、连接、操作队列和运行状态。

## 已确认关系

```text
账号主 1 ──拥有── N 个闲鱼账号
闲鱼账号 1 ──对应── 1 个逻辑 Account Runtime
API 调用者 ──指定 account_id──> 闲鱼账号
```

- “账号主”和“闲鱼账号”是两个独立概念。
- 一个账号主可以提供多个闲鱼账号。
- 每个闲鱼账号的运行状态、凭证、操作和日志保持隔离。

## 托管操作关系

- 平台是托管期间的默认运营方，但不独占闲鱼账号的使用权。
- 账号主仍可登录闲鱼并进行手工操作。
- 账号主的手工操作属于外部状态变化，需要同步到平台状态和审计记录。
- 需要账号主或内部人员直接操作时，账号可以进入“人工操作模式”。
- 人工操作模式下，暂停可能冲突的相关平台命令；退出后重新同步状态再恢复执行。

## 闲鱼账号托管生命周期与 Runtime 状态

账号状态拆成两个正交字段，不把托管关系和连接状态混为一个枚举。

### 账号生命周期

```text
pending
→ authorizing
→ hosted
→ paused
→ hosted
→ ending
→ ended
```

- **`pending`**：已经登记合作关系，尚未开始闲鱼登录授权。
- **`authorizing`**：账号主正在完成登录或验证。
- **`hosted`**：托管关系生效；Runtime 是否可执行由独立状态决定。
- **`paused`**：保留登录资料，停止平台业务操作，之后可以恢复。
- **`ending`**：停止任务、撤销 Runtime 租约并清除凭证。
- **`ended`**：当前托管关系结束；业务记录按结算与审计周期保留，之后删除或匿名化。

### Runtime 状态

```text
offline → starting → connecting → online
                              ↘ degraded
                              ↘ needs_login
                              ↘ needs_verification
                              ↘ manual_control
online / degraded / manual_control → draining → offline
```

- `online` 代表当前 Worker、Session、原生连接和心跳可用；
- `degraded` 代表 Runtime 仍存活，但部分能力、连接或同步受限；
- `needs_login` 和 `needs_verification` 只改变运行能力，不结束托管关系；
- `manual_control` 代表账号主正在直接操作，冲突 Command 暂停；
- 一个账号同时只有一个活动 Runtime 执行租约。

例如，`hosted + needs_login` 表示账号仍在托管，但正在等待账号主重新授权；`paused + offline` 表示暂停运营且 Runtime 已停止。

账号主可以导出与自己账号相关的数据。凭证清除、数据导出、删除和匿名化过程都需要生成审计记录。

## 商品模型

### 平台商品模板

平台内部维护的可复用商品定义，包含标题、文案、图片、默认价格和其他商品资料。它本身不是闲鱼上的真实商品。

### 闲鱼商品

发布在某个闲鱼账号下的真实商品实例，拥有独立的 `account_id`、闲鱼 `item_id`、实际价格、上下架状态和运营数据。

### 关系

```text
平台商品模板 1 ──发布──> N 个闲鱼商品
闲鱼账号 1 ──拥有──> N 个闲鱼商品
```

- 同一个平台商品模板可以发布到多个闲鱼账号。
- 每个闲鱼商品可以单独覆盖价格、文案和上下架状态。
- 平台可以把模板更新批量同步到选定的闲鱼商品。
- 模板变更和闲鱼商品实际状态分别记录，避免把批量意图误认为平台已经执行成功。

模板编辑只改变平台商品模板，不自动改变已经发布的闲鱼商品。模板同步必须通过显式 `item.template.sync` Command，指定目标账号和商品；每个目标商品独立产生 Operation 和结果。

## 买家身份

### 闲鱼买家

由闲鱼用户 UID 标识的外部交易方。同一个闲鱼买家可能同时与多个托管账号产生会话和订单。

```text
闲鱼买家 1
  ├── 在卖家账号 A 下产生会话和订单
  ├── 在卖家账号 B 下产生会话和订单
  └── 在卖家账号 C 下产生会话和订单
```

- 系统内部按闲鱼用户 UID 识别同一个买家。
- 会话、消息和订单始终保留具体卖家账号归属。
- 平台可以在权限允许时查看买家的跨账号历史。
- 合作账号主只查看与自己账号相关的数据。
- 第一阶段先保存稳定买家标识，跨账号分析能力后续建设。

## 会话和订单模型

### 会话

一个会话由卖家账号、买家和主商品共同唯一确定：

```text
seller_account_id + buyer_uid + primary_item_id
                    ↓
                唯一会话
```

- 同一买家从同一卖家账号的同一商品进入时，复用原会话。
- 同一买家从不同商品进入时，创建新的会话。
- 每个会话绑定且只绑定一个主商品，`primary_item_id` 创建后保持不变。
- 主商品下架或删除后，会话仍保留原商品关系。
- 会话消息可以引用其他商品卡片，但不会改变主商品。

### 订单

- 一个会话可以关联多个订单，例如取消后重新下单。
- 每个订单归属一个卖家账号、一个买家、一个实际购买商品和一个对应会话。
- 当前会话关联的订单属于该会话的主商品。
- 买家购买其他商品时，订单归属另一个商品对应的会话。

### 关系

```text
闲鱼账号 1 ──拥有──> N 个闲鱼商品
闲鱼商品 1 ──产生──> N 个会话
闲鱼买家 1 ──参与──> N 个会话
会话 1 ──关联──> N 个订单
```

## 评论和评价模型

### 商品评论

买家或其他闲鱼用户在商品下产生的公开评论或留言。商品评论直接归属闲鱼商品，不要求存在订单。

### 交易评价

订单完成后，买卖双方围绕该笔交易产生的评价。交易评价直接归属订单，再通过订单关联卖家账号、买家和商品。

```text
闲鱼商品 1 ──拥有──> N 条商品评论
订单 1 ──拥有──> 买家评价 / 卖家评价 / 后续评价内容
```

- 商品评论和交易评价使用独立的数据模型与 API。
- 商品评论的管理能力跟随商品权限。
- 交易评价的管理能力跟随订单和平台实际开放状态。

## 媒体模型

### 平台素材

平台保存的原始图片、视频、音频或文件。平台素材与具体闲鱼账号解耦，可以被商品模板、消息和其他业务对象复用。

### 闲鱼媒体实例

平台素材上传到某个闲鱼账号后形成的账号级平台资源，记录目标账号、闲鱼上传结果、平台 URL、资源状态和过期信息。

```text
平台素材 1 ──上传到多个账号──> N 个闲鱼媒体实例
平台商品模板 ──引用──> 平台素材
闲鱼商品 / 消息 ──引用──> 对应账号的闲鱼媒体实例
```

- 原始素材只需维护一份。
- 每个账号的上传结果和平台资源状态独立记录。
- 闲鱼媒体 URL 失效时，可以从平台素材重新上传。
- 商品和消息可以复用同一平台素材，但执行时使用目标账号对应的闲鱼媒体实例。

## 标准执行语言

### Capability

系统声明支持的一项闲鱼能力，例如 `message.send` 或 `item.price.update`。

### Command

API 调用者要求系统执行的具体命令，包含目标 `account_id`、能力名称、操作参数和幂等标识。

### Operation

一次 Command 对应的实际执行过程。Operation 拥有独立 ID、状态、时间、执行结果和错误信息。

### Event

系统中已经发生的事实，例如收到消息、开始执行、闲鱼确认成功或登录态失效。Event 用于通知和追踪，不表达未来意图。

```text
Capability：item.price.update
Command：把账号 A 的商品 X 改成 99 元
Operation：本次改价执行 OP-123
Event：accepted → started → succeeded
```

### 成功语义

- `accepted` 只表示系统已经接收 Command，并返回 `operation_id`。
- `accepted` 不代表闲鱼操作完成。
- 只有闲鱼返回成功确认，或系统观察到目标状态已经生效，Operation 才进入 `succeeded`。
- 失败、超时、需要登录和需要平台验证必须使用独立终态或阻塞状态表达。

## 标准 API 形态

完整能力基座同时提供三类接口：

### Query

读取闲鱼或 Account Runtime 的当前状态，不改变业务对象。

### Command

要求系统执行具体操作，并创建可追踪的 Operation。

每个底层 Command 只指定一个 `account_id`。跨账号批量任务由上层编排系统拆分为多个单账号 Command，每个账号产生独立 Operation 和结果。

### Event

通知调用者已经发生的消息、状态变化和执行结果。

```text
Query   = 眼睛：读取当前状态
Command = 手：执行具体操作
Event   = 耳朵：接收外部变化和执行结果
```

- 每个核心业务域都需要同时考虑查询、操作和事件能力。
- Command 成功后仍可以使用 Query 验证最终状态。
- 闲鱼主动产生的变化通过 Event 进入系统，再更新本地状态。

## 平台状态与本地业务记录

闲鱼是平台业务状态的最终来源；XianYuApis 同时维护标准化的本地业务副本和历史账本。

本地记录至少包括：

- 消息和会话历史；
- 商品状态及其变更；
- 订单和履约状态；
- 商品评论和交易评价；
- Command、Operation、Event 及最终结果；
- 账号在线、掉线、验证和重新登录记录。

本地记录用于查询、恢复、补偿、审计和后续上层业务，不把本地“预期状态”误认为闲鱼已经完成的真实状态。系统重启或断线恢复后，需要通过 Query 和游标补齐遗漏事件。

## 账号首次同步

闲鱼账号首次接入时，系统建立初始业务快照，再进入增量同步：

```text
登录授权
→ 同步现有商品
→ 同步可访问的会话和消息
→ 同步订单、评价和相关状态
→ 建立各业务域同步游标
→ 持续增量同步
```

- 历史同步范围支持全部可访问历史、最近 30/90 天或从托管当天开始。
- 默认尽量导入闲鱼当前可访问的历史数据。
- 数据量较大时允许后台分批补齐，不阻塞账号进入基本可用状态。
- 每个业务域分别记录同步范围、游标、缺口和最后成功时间。

初始同步 API v1 将这些记录具体化为三个独立 `SyncJob`：商品、会话与消息、订单与评价。默认按该顺序调度，但任一域都可以单独查询、重试和补齐。
