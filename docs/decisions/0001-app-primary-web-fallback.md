# ADR-0001：App 原生 IM 作为主路线，Web 作为回退

- 状态：Superseded by ADR-0011
- 日期：2026-07-26

> 2026-07-28：产品执行架构已经收敛为纯 App 原生路线。Web/Cookie 只保留为历史研究和数据工具，不再作为生产回退通道。

## 背景

现有项目基于 Cookie 的 WebSocket 和 MTop 请求，已经能够支撑历史导出及 Web 端实时通信，但登录态刷新、长连接恢复和验证码处理带来维护成本。Mac 上已经安装了闲鱼 App，App 内部存在 AIM/ACCS 原生 IM 服务和完整会话状态。

## 决策

采用双传输边界：

1. App 原生 AIM/ACCS 作为单账号实时 IM 的主路线。
2. 现有 Web/Cookie WebSocket 保留为回退、对照和数据导出路线。
3. 业务层通过 `Transport` 抽象接入两条路线，不把 Cookie、AIM 序列号或 App 对象泄漏到业务规则中。
4. 先完成单账号原生收发闭环，再评估无界面会话和多账号调度。

## 原因

- 登录态、设备态、心跳和重连由 App 原生组件维护，减少 Python 侧协议复制。
- 原生 AIM 已经提供收消息回调、文字发送和回复对象。
- 单账号先行可以得到真实的回调字段、错误码和时序，再决定独立协议客户端的范围。
- 保留 Web 路线可支持回归测试和原生链路短暂离线时的业务连续性。

## 代价和边界

- 原始签名 App 默认受 macOS 调试权限限制，动态插桩需要测试副本或可调试构建。
- App 进程、登录态和网络在线状态仍是原生主路线的运行前提。
- 静态出现的 MTop API 名称只代表客户端表面，不代表请求参数和权限已确认。

## 后续触发条件

当单账号收发、重连、去重、已读和错误观测全部通过后，再决定：

- 是否把 AIM/ACCS 会话抽成独立 Native Worker；
- 是否实现统一 `NativeAppTransport`；
- 是否进入多账号 Session Vault 和 Worker Pool 设计。
